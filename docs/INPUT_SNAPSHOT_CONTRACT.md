# Local P2 evidence snapshot format

The CLI and loopback UI accept a bounded JSON object. This is a local calculation format, not a Fab Insight MCP API contract. The v1 shared evidence envelope remains the public output contract; this file documents only the P2 input adapter boundary.

## Required process event

Each `events[]` object contains `wafer_id`, `step_instance_id`, `operation`, timezone-aware ISO-8601 `timestamp`, `source_id`, `relationship_id`, and `approved_relationship: true`. A boolean approval flag by itself is never source provenance. `step_instance_id` identifies one occurrence, including rework. `timestamp` is event/effective time; optional `recorded_at` preserves record-ingestion time separately. Optional `time_uncertainty_seconds` declares a non-negative clock uncertainty range. Optional processing bounds and their independent uncertainty values describe actual processing intervals. Overlapping time ranges are retained as unresolved groups; the engine does not claim within-group order.

Other optional event fields include `identity_relationship_id`, `tool_id`, `chamber_id`, `processing_start` + `processing_end`, `route_id`, `route_version`, `rework_of_step_instance_id`, and `lot_id`. The pair of processing bounds must be complete and timezone-aware. A blank tool, chamber, lot, route, or relationship value is invalid; use JSON `null` when unknown. `lot_id` describes membership at that event only.

Source-linked rows require a `sources[]` entry with `id`, `approved_semantic_version`, `grain`, `source_hash`, and optional string `permissions_ref` and `observed_at`. They also require a `relationships[]` entry with `id`, `approved: true`, `source_ids`, `keys`, `cardinality`, `grain`, and timezone-aware `effective_start` / `effective_end`. Each event names the relationship ID that covers its source; that relationship must declare `wafer_id`, `step_instance_id`, and `timestamp`, include its other join-key fields in the event, and be effective across the event-time uncertainty interval. Optional fields used in an analysis must also be declared by the source relationship: `lot_id` for event-row membership context, `route_id` and `route_version` for route conformance, `rework_of_step_instance_id` for rework, and `operation_definition_id` for definition links. An undeclared `lot_id` is labeled `EVENT_LOT_FIELD_UNVERIFIED` and is not used to attach material relationships to the event. Exact tool or chamber exposure additionally requires the event relationship to declare the selected equipment field (`tool_id` or `chamber_id`). If processing interval bounds are present, the relationship must declare `processing_start` and `processing_end`. If the relationship does not declare the scope and time fields used, the event cannot establish an exact exposure; affected population members remain unknown.

If the same wafer token occurs in multiple sources, each event must also name one approved `identity_relationship_id`; its relationship record must set `entity_identity: true`, cover the source IDs, include the `wafer_id` key, and be effective across each event's full clock-uncertainty interval. If an interval crosses the identity mapping's effectivity boundary, the local candidate refuses the cross-source merge. It does not normalize aliases or infer identity from matching strings.

## Optional investigation fields

For exact exposure using actual `processing_start` / `processing_end`, the event source relationship must declare both fields and cover the full timestamp uncertainty plus the entire processing interval uncertainty. If either end crosses relationship effectivity, exact exposure and nonmatch classification remain unknown, even when the point timestamp itself is effective.

- `wafer_id`: target for a backward journey. Without an explicit `cohort`, an exposure query is scoped to this target wafer.
- `target_wafer_ids`: optional non-empty, duplicate-free target list for an abnormal wafer cohort. If both target fields are present, `wafer_id` must be one member of `target_wafer_ids`. Target rows must exist in the submitted event snapshot; without an explicit `cohort`, exposure scope uses the target list.
- `target_lot_id`: optional lot start. The selected lot's outcome rows must explicitly contain the same `lot_id`, and each row's declared source relationship must include both `lot_id` and `wafer_id` keys. At least one selected outcome must be `ABNORMAL`; normal outcomes in that lot remain in the cohort as counterevidence. If `target_wafer_ids` is also supplied, it must exactly match the wafers in those outcome rows; `wafer_id`, if supplied, must be one of them. This derives membership from supplied rows only and does not prove the snapshot includes every lot member.
- `cohort`: explicit wafer population for forward exposure classification.
- `suspected_exposure`: either `{chamber_id, start, end}` or `{tool_id, start, end}`, with timezone-aware half-open bounds `[start,end)`. Optional `condition_type` is `PROCESS`, `MAINTENANCE`, or `CHANGE`; it is a caller-supplied interval label and does not verify that a maintenance/change event occurred. When both equipment IDs are present, chamber is the selected scope and `tool_id` is context. Tool-only scope matches the exact event `tool_id`; it never infers a chamber from equipment groups. Missing selected-equipment assignment or uncertain time is possible exposure, not a confirmed match. The output distinguishes caller-supplied condition context from source-verified event evidence.
- `condition_events[]`: optional source-linked condition records with `condition_event_id`, `condition_type`, exact `equipment_type` (`TOOL` or `CHAMBER`), `equipment_id`, timezone-aware `event_start` and `event_end`, `source_id`, and `relationship_id`. A matching relationship must declare each event field. `time_uncertainty_seconds`, `recorded_at`, and `source_hash` are optional. Exact duplicate rows are coalesced; conflicting duplicate IDs refuse the snapshot. Matching records are reported as temporal context only. A condition event overlapping a selected window does not prove that processing was exposed to its effects or establish a cause.
- `coverage`: `{complete, covered_wafer_ids, source_ids, covered_source_ids, relationship_id, record_id, window_start, window_end, missing_record_ids}`. `source_ids` identify the source of the coverage record; `covered_source_ids` identify event sources whose observation coverage is asserted. The named approved relationship must connect the coverage source and declare `record_id`, `complete`, `covered_wafer_ids`, `covered_source_ids`, both window fields, and `missing_record_ids`; its effective interval must contain the coverage window. The record must cover every queried wafer and the full exposure window, include every event source used in the population, and provide a unique explicit list of missing record IDs. Any listed missing record prevents complete coverage, so nonmatches remain `UNKNOWN` and cannot be used as unaffected comparators. Without this source-linked record, nonmatches remain `UNKNOWN`. Even an accepted record is caller-declared in this local snapshot and is not authenticated against a live service.
- `operation_definitions[]`: optional separate approved records with `operation_definition_id`, `operation`, `source_id`, `semantic_version`, `relationship_id`, `approved: true`, and effective bounds. If any definitions are supplied, every process event must name a matching definition; labels must agree and be effective at event time. Step instances remain separate from definitions.
- `material_relationships[]`: optional typed source-linked edges with a unique `record_id`, declared `relationship_type`, typed `from_entity` and `to_entity` endpoints, `key_values`, `effective_start`, `effective_end`, `observed_at`, `source_id`, and `relationship_id`. The relationship record must declare the same relationship type and all key values. Edges retain relationship/source/hash provenance. Only source-provided relationships are traversed; split, merge, and lot membership are not inferred from matching IDs. For each process event, the full timestamp uncertainty interval is compared with edge effectivity. An edge is `EFFECTIVE_ACROSS_EVENT_TIME_UNCERTAINTY` only when the entire interval is inside its half-open effectivity range; an intersecting edge is shown as `POSSIBLY_EFFECTIVE_DUE_TO_CLOCK_UNCERTAINTY`. Lot membership crossing an edge boundary is `TEMPORALLY_AMBIGUOUS_MEMBERSHIP`, with candidate lot IDs listed instead of a single asserted membership. Lineage traversal follows only source-declared `SPLIT_FROM` and `MERGED_FROM` lot-to-lot edges, preserves edge direction and provenance, and never traverses through `LOT_MEMBERSHIP` into sibling wafers. Reachable multi-hop relationships are time-filtered for each event; uncertain path edges keep the path explicitly possible.
- `material_relationship_coverage`: optional caller-declared completeness record with `record_id`, `complete`, typed `covered_entities`, `covered_relationship_types`, `covered_source_ids`, coverage `source_ids`, `relationship_id`, `window_start`, `window_end`, and `missing_record_ids`. Its approved relationship must declare those fields; its source and relationship must be effective over the window; the window must contain the event's entire clock-uncertainty interval; and the declared entity/type/source set must contain the observed lineage seeds, endpoints, and edge sources. Required edge types include `SPLIT_FROM` and `MERGED_FROM`, plus `LOT_MEMBERSHIP` when membership edges establish the seed. A complete result is labeled `CALLER_DECLARED_SOURCE_LINKED_COMPLETE`, never live-source authenticated. Missing, invalid, omitted, or out-of-window evidence stays `INCOMPLETE_OR_UNKNOWN` or `NOT_ESTABLISHED`; absent edge rows alone do not establish absent lineage.
- `history_coverage`: optional `{complete, covered_wafer_ids, source_ids, covered_source_ids, relationship_id, record_id, window_start, window_end, missing_record_ids}` record. `source_ids` identify the coverage record source; `covered_source_ids` identify event sources whose process observations are asserted complete. The coverage relationship must declare every record field and span the coverage window; each covered event source must also have a relationship declaring `wafer_id`, `step_instance_id`, and `timestamp` effective across that window. Coverage is labeled `COVERAGE_DECLARED_COMPLETE` only when every covered wafer's observed event sources are included, all event uncertainty bounds fit inside the window, and no records are named missing. The caller's assertion is still not authenticated; absent/partial coverage remains explicit as `COVERAGE_UNKNOWN` or `INCOMPLETE`. This status applies to the process event history, not completeness of separately supplied material edges. Per-wafer chronology ambiguity remains separate.
- `expected_routes[]`: caller-declared approved `{route_id, route_version, approved, source_id, relationship_id, operations, allowed_sequences?}` records. The named approved route-definition relationship must include that source and declare `approved`, route ID/version, `operations`, and `allowed_sequences` when exceptions are present. Its effective interval must contain every event's full clock-uncertainty interval before conformance can be asserted. Segment evidence preserves the route source, relationship ID, and effective bounds; local declarations remain unauthenticated against a live service. Each `allowed_sequences[]` value is an explicit approved sequence exception. `route_coverage` uses the same source-linked coverage record shape as `coverage`; its `covered_source_ids` must include the event sources and the approved expected-route source, and its window must contain the submitted event-time uncertainty bounds. Missing or unlinked coverage produces `COVERAGE_INCOMPLETE`; route-definition effectivity that misses event uncertainty produces `ROUTE_DEFINITION_EFFECTIVITY_UNCERTAIN`. A sequence mismatch is an observed difference for review, not a process violation. Rework steps with a verified explicit predecessor reference are retained as rework and excluded from the base route sequence.
  Route-variant counts identify their denominator as observed event-bearing wafers with determinate chronology. The separate `route_population_summary` reports any caller-declared covered population, observed histories, chronology-uncertain wafers, declared members with no event rows, and event wafers outside declared coverage. No path is inferred for a covered member with no submitted event rows, and local coverage acceptance does not authenticate the caller's claim.
- `outcomes[]`: `{wafer_id, label, timestamp, source_id, relationship_id, approved_relationship}` where label is `NORMAL` or `ABNORMAL`; optional `lot_id` records the caller-declared lot at outcome time. The source must appear in `sources[]`; the approved relationship must declare `wafer_id` and `timestamp` (and every other declared key), cover the outcome source, and be effective at the timezone-aware outcome timestamp. Product IDs enter mix strata only when the outcome relationship also declares `product_id`. For a `target_lot_id` start, the relationship must also declare `lot_id`. These values are used only for descriptive cohort and counterevidence analysis.

Every event, material edge, condition event, outcome, and coverage record used in an analysis must reference a source record and an explicit effective-dated relationship record. Exposure and counterevidence outputs separately report definitely exposed, potentially exposed, unknown, and not-observed-exposed populations. Not-observed-exposed requires a source-linked coverage record, but that record remains caller-declared until authenticated by an authorized live source. Counterevidence records supporting and contradicting observations, missing outcomes/relationships, available product/time/equipment strata, and a next logical verification. It reports no statistical association unless an explicit method is added and never establishes causality. Synthetic examples include visibly synthetic source records; those records do not authenticate company authorization, source semantics, or data rights. Real internal mode is intentionally unavailable in this candidate.

## Local request limits

The loopback server rejects request bodies over 25 MiB, event arrays over 100,000 rows, and outcome arrays over 100,000 rows. The CLI enforces the byte bound before parsing, and the deterministic engine also refuses an oversized outcome list when called directly. UI preflight shows the payload, event, and outcome counts and their local limits. These are local snapshot bounds, not authorized MCP query limits or proof of source permission.
